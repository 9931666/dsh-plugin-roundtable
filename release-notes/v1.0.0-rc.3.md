# RoundTable v1.0.0-rc.3

**视觉与交互修复版：让界面在深色主题下成立，并把四个交互/性能缺陷修掉。**

这一版的全部改动来自一次**对抗式评审**（用针锋 Crossfire 对圆桌的视觉设计做红队审查，
红队只读源码取证，逐条给出文件与行号）。没有新功能。

> **发行渠道：npm + GitHub Release。** 包名 `@y9931666/dsh-plugin-roundtable`
> （作者的 npm 账户名；早期文档里的 `@huanlin/...` 属于另一个用户，不可用）。
> 本版是**预发布**（`1.0.0-rc.3`），进 npm 的 `next` 渠道，安装要带标签：
> `dsh plugin --profile web add @y9931666/dsh-plugin-roundtable@next`
> （源码安装：`git clone https://github.com/9931666/dsh-plugin-roundtable` → `pnpm install` → `pnpm build` → `dsh plugin --profile web add .`）
>
> 宿主基线：**DeepSeek Harness 0.2.0-rc.2**

---

## 0. 一句话

圆桌的浏览器半体此前**一个主题令牌都没用**：两个样式表里 `#ffffff` 底色与
`rgba(0,0,0,.4~.85)` 文字全部写死。**深色主题下前景与背景亮度差趋近于 0 —— 整页看起来"什么都没有"。**
本版把 315 处硬编码颜色换成宿主的 13 个 alias 令牌，并修掉 4 个交互/性能缺陷。

---

## 1. 深色主题整片不可读（最严重）

**症状**：把外观切到深色后，「圆桌会议」标签页的文字、面板、弹窗仍是浅色值。
空状态（`空标题 + 空提示`）尤其明显：两个类都只用写死的近黑文字、自身不设背景，
落点是宿主那张**随主题翻转**的会话底色。

**修法**：全部换成宿主 `@deepseek-ai/dsh-client-ui-theme` 的 alias 令牌 ——
底色 `bg-base/bg-layer-1/bg-layer-2/bg-overlay`、文字 `label-primary/label-secondary`、
边框 `border-l1/border-l2`、状态 `state-{error,success,warn,idle}-primary`、
品牌 `brand-primary`。透明变体统一用 `color-mix(in srgb, var(--token) N%, transparent)`
（宿主自身 CSS 就在用这个语法）。

**保留的例外**（有就地注释）：第三方品牌 logo 色（`PROVIDER_BRAND`，商标色无法用令牌表达）、
品牌色填充上的白字、主持人锚点的刻意深色底、红色圆点上的白色 ×。

## 2. 蓝色强调曾映射到"单色令牌"

`--dsw-alias-brand-primary` 实测是**单色**（浅色 `#0f1115` / 深色 `#f9fafb`），
宿主自己只用它 2 次 —— 它**不是强调色**。把它用在蓝色强调上，会让端口描边、
拖拽线、消息脉冲、开关 accent 在浅色下变近黑、深色下变近白，**蓝色身份丢失**。

**修法**：32 处蓝色强调改用宿主真实的强调蓝
`--dsw-alias-brand-primary-new-colorprimary-new-color`
（浅色 `#4176e6` / 深色 `var(--dsw-static-deepseek-450)` = `#5686fe`，
宿主自用 14 次，用法同构：图标色 / chip 底 / 徽标填充 / focus 指示条 / 时间线 rail）。

顺带修掉三处因此暴露出来的自相矛盾：
- `.msgPulse`：蓝色辉光围着**近白**圆点 → 圆点与辉光统一为强调蓝；
- `.port:hover`：蓝色描边 + 悬停填**近白** → 与描边统一为强调蓝；
- `.manageAddBtn`：深色下白字压**近白**底 → 文字色改用 `--dsw-alias-label-primary-foreground`
  （宿主 primitives 里"填充上的文字色"：浅色 `#fff` / 深色 `#0f1115`）。

## 3. 评审弹窗里的操作**看不到任何反馈**

**症状**：在弹窗里点「支持（认定为缺陷）」，或空理由点「确认驳回」，界面毫无回执。

**根因**：所有表态反馈都只走 `setToast`，而 toast 的唯一渲染点在 `.canvas` 内、
`z-index: 6`；弹窗遮罩 `.manageOverlay` 是 `position: fixed; inset: 0; z-index: 1200` ——
**toast 被压在整屏 35% 遮罩之下**，且 860px 居中的弹窗卡片正好盖住画布顶部同一区域。
三条专为弹窗写的文案在界面上**不可达**。

**修法**：按"有没有弹窗"决定渲染层级 —— 无弹窗时仍留在画布内（观感零变化），
有弹窗时挂到 `.root` 直属层级并 `position: fixed; zIndex: 1300`。一处改动覆盖知识库/管理/评审三个弹窗。

## 4. 拉线端口可聚焦，但键盘**不可能完成连线**

**症状**：每个节点有 4 个 11px 端口，带 `role="button"`、`tabIndex={0}`、
`aria-label="connect"`，CSS 还专门写了 `.port:focus-visible` —— 但唯一入口是 `onMouseDown`，
延续依赖 window 上的 `mousemove/mouseup`。Tab 能停在 20 个端口上，按 Enter/空格**无任何反应**。

**修法**：实现真键盘闭环 —— Enter/空格选中起点（toast 提示）→ 在另一节点端口 Enter 落点；
同节点再 Enter 或 Esc 取消；补 `aria-pressed`。落点判定与鼠标**共用同一个 `connectNodes()`**，
不存在两套实现。

## 5. 拉线时每个 `mousemove` 重渲染整棵树

**症状**：`mousemove` 直接 `setDrag`，无节流无合帧；effect 还把 `drag` 放进依赖数组，
于是**每个鼠标事件**都拆除并重挂一对 window 监听器，并重建整棵子树（含边几何与时间格式化）。

**修法**：rAF 合帧 + 用 ref 持有最新坐标（mousemove 只同步写 ref，按帧 setState），
effect 依赖由 `drag` 改为布尔量。落点判定改用 ref 里的真实坐标，**不依赖上一帧渲染坐标**，
避免"指针停下时线停在上一帧"。

## 6. 边几何 O(E²)

**症状**：`renderEdge` 内对**每条边**重复扫描整个 `meeting.edges`，且与数据是否变化无关。

**修法**：一次 O(E) 建 `edgeFanTable`（出/入度 + 组内序号，序号语义与原实现逐字等价），
`renderEdge` 与 `edgeRemoveDots` 两处改查表。**几何结果与改前逐位一致**，行为零变化。

## 7. 三态按钮的颜色语义与针锋插件相反

圆桌里「支持（认定为缺陷）」是**红色系**、「驳回」是**绿色系**；
而针锋 Crossfire 的约定相反（认定=绿、驳回=红）。同一用户在两个界面间切换时**读色等于反向读数**。

**修法**：按语义对调为「认定=success / 驳回=error」，并留注释说明"与针锋 Crossfire 约定一致"以防回归。

## 8. 工具卡片里的写死琥珀色

`tool-views.tsx` 的 `WARN` 用了写死的 `#e0a030`，卡片边框也是硬编码灰色 ——
同属深色主题隐患。已改为 `--dsw-alias-state-warn-primary` 与 `--dsw-alias-border-l1`。

## 验收与已知限制

- `npm.cmd run typecheck` → exit 0；`npm.cmd run test:inline` → **150 / 150 pass**。
- 两个样式表所用令牌经脚本校验：**全部在宿主白名单内，无自造令牌名**
  （自造名在深色下会静默失效，是最隐蔽的失败方式）。
- **需要人眼确认**（代码无法验证主观观感）：深色主题下的整体观感与对比度、
  拖拽合帧后的跟手度、弹窗回执是否确实浮在遮罩之上、键盘连线路径的手感。
- 未做：颜色之外的主题维度（字号/间距并非本次目标）。
