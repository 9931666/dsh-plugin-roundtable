# RoundTable v1.0.0-rc.1

**第一个 1.0 候选版本。这一版不是加功能，而是把「插件能不能长期自己活下去」这件事补齐：
宿主支持矩阵成为可校验的单一来源、版本差异收敛进一个模块、发布与诊断变成可执行的门禁。**

> 发布渠道：**`next`**（预发布）。验证通过后再用 `npm dist-tag add` 把**同一份产物**提升为 `latest`。
>
> 宿主基线：**DeepSeek Harness 0.1.5-rc.3**

---

## 0. 为什么是 1.0

此前插件的"成熟度"取决于维护者的记性：改动散在工作区、版本漂移靠人发现、
发布靠临场操作。这一版把这些变成了**代码与门禁**：

| 问题 | 之前 | 现在 |
| --- | --- | --- |
| 支持哪些宿主？ | 散落在 docs / package.json / 注释里各说各话 | `compatibility.json` 唯一来源，`scripts/compatibility.mjs` 强制一致 |
| 宿主 API 变了怎么办？ | 散落 5 个文件里各自判断 | 收敛进 `src/harness-compat.ts` 一处 |
| 发布前该确认什么？ | 靠记性 | `scripts/release.mjs` 九项检查，含产物 SHA-256 |
| 用户报"界面不见了"怎么查？ | 来回猜、要日志 | `scripts/doctor.mjs` 一条只读命令给证据 |

## 1. 宿主支持矩阵（B2 · 新）

新增 `compatibility.json` 作为**矩阵与能力清单的唯一来源**，并由
`scripts/compatibility.mjs` 校验四份声明彼此一致：

1. 矩阵里的 `required` / `optional` 能力清单；
2. `package.json` 的 `devDependencies`（**类型基线**）必须精确指向 `recommendedHost`；
3. `package.json` 的 `peerDependencies` 区间必须覆盖该基线；
4. `src/harness-compat.ts` 的 `CAPABILITY_SPECS` 必须登记每个能力的探测点。

> **为什么这条最重要**：devDependencies 决定消费者 `npm install` 后拿到哪一版
> 类型。基线漂了，表现是"本机全绿、用户装完就坏"，而这类故障最难查。

矩阵同时记录 `baseline.packages`（17 个包）与 `previewTag`。

## 2. 兼容边界集中化（B1 · 新）

新增 `src/harness-compat.ts`，**所有与 DSH 版本相关的形状集中于此**，做法借鉴社区
项目 dsh-agent-teams 的 `harness-compat.ts`：

- `CAPABILITY_SPECS`：12 个探测点，每项记录用途、**失效时用户看到什么**、证据；
- `optionalService()` / `webRouteHostOf()` / `workspaceRegistryOf()`：服务探测
  统一入口，**探测结果留痕**（每个能力只记第一条，避免轮询刷爆）；
- `asDisposer()` / `effectWithOptionalDisposer()`：`rpc.handle` 返回值形状判定；
- `projectionValuesOf()`：`sessionProjections` 读取，绝不抛错。

两条铁律写在模块头上：**探测绝不成为新的加载门禁**；**降级必须留痕**。

原先散在 `index.ts` / `rpc.ts` / `token-usage.ts` 的版本判断与结构式服务探测已迁移进来。

## 3. 修掉一处真实的类型基线漂移（体检发现）

按新门禁对 rc.3 跑体检时，`compatibility.mjs` **当场报出 19 项失败**：

- `package.json` 没有显式的宿主基线声明；
- **17 个 devDependencies 仍指向 `0.1.5-rc.2`**，而本机运行的是 `0.1.5-rc.3`；
- `HARNESS_RANGE` 也硬编码着 rc.2。

全部对齐到 rc.3，并补上 `package.json` 的 `roundtable.hostBaseline`。

## 4. 修掉 cordis 混装导致的全量类型错误

对齐基线后第一次对 rc.3 类型跑 `tsc`，**60+ 处报错**，形如：

```
Property 'subagents' does not exist on type 'Context'
Argument of type '"subagent/end"' is not assignable to parameter of type 'keyof Events'
```

**根因不是 rc.3 破坏了 API**，而是**两处 `@deepseek-ai/cordis@4.0.2` 是不同物理副本**：
宿主与插件各有一份，TypeScript 视为两个不同模块，于是
`declare module '@deepseek-ai/cordis' { interface Context { … } }` 的声明合并失效。

把插件的 cordis 指向宿主那一个副本后，`tsc` **0 错误**。
`scripts/doctor.mjs` 现在会主动比对这两条路径，并在不一致时给出上面这段解释。

> 这是本版最有价值的一条经验：**rc 线上"类型全红"不一定是 API 破坏，先查是不是混装。**

## 5. 发布门禁与产物验证（A1 · 新）

新增 `scripts/verify-package.mjs`（19 项检查）：

- `files` 清单非空；`main` / `types` / `exports` / `dsh.bundle.patch` 指向的文件
  在仓库里**真实存在**；
- `cordis.patch.yml` 在 `files` 里 —— 不在的话消费者装上后插件不会被注册；
- 产物 `lib/` 里没有 `.ts/.tsx` 残留；
- **每个宿主侧源码模块都在产物里有痕迹**（强检查：所有 `lib/*.js` 拼起来必须
  提到每个模块的导出符号）。

> 最后这条替代了原先的"相对导入 → 同名 `.js`"检查：打包器会做
> code-splitting，那种检查恒真、等于没检查。

**顺带省掉 557 kB**：`lib/client.js.map` 此前被一起发布（占解包体积 36%），
而浏览器半体是宿主直接加载的 bundle，默认不会去取它。sourcemap 改为按需
（`RT_SOURCEMAP=1`）打开。

## 6. 发布护栏（A2 · 新）

新增 `scripts/release.mjs`：

- **渠道判定**：预发布只能进 `next`，稳定版才允许进 `latest`；
- **防 latest 倒退**：稳定发布前查 registry，比现有 latest 更低就拒绝；
- **首次发布识别** + scope 归属提醒（`@huanlin` 无权限时是 403 而非 404）；
- **产物指纹**：打包候选 tarball 并输出 SHA-256 / SHA-1 / integrity。

**刻意不调用 npm 命令**：registry 走 HTTPS 直连、打包用内置 ustar 实现，
于是这个门禁在任何环境都跑得动（本机 npm 全局缓存在沙箱外，Windows 上脚本化
调用 `npm.cmd` 也会 EINVAL/EPERM）。

## 7. 只读诊断（A3 · 新）

新增 `scripts/doctor.mjs`：报告宿主/插件精确版本与位置、**探测混装**（同族包
多版本）、**比对 cordis 实例同一性**、打印能力清单。它**不执行插件、不修改配置**，
并且明确声明：**通过 ≠ 插件能用**，它只排除安装层故障。

## 8. 工程修补

- 补声明 `@deepseek-ai/dsh-client-ui-renderer`（`dsh.client.inject` 里一直在用，
  却不在任何 dependencies 中）；
- `HARNESS_RANGE` 与 `COMPATIBILITY.recommendedHost` 由测试强制一致；
- 新增 npm scripts：`compatibility` / `verify:package` / `doctor` / `release` /
  `publish:guard`。

## 已知边界

- **rc.3 之外的宿主未验证**。矩阵目前只有 `0.1.5-rc.3` 一条；`0.1.6-alpha.*` 是
  另一条线，未纳入。
- **预发布升级路径**：先发到 `next`，自行安装验证后再
  `npm dist-tag add @huanlin/dsh-plugin-roundtable@1.0.0-rc.1 latest`。
  **不重新打包** —— 提升标签的必须是同一份字节。
- **前端测试仍为零**：`RoundTableView.tsx`（1,723 行）没有测试覆盖，因为它需要
  先把纯逻辑从组件里抽出来。这是已知欠账，不影响本版发布。
- `git` 里的 `pnpm-lock.yaml` 与 `devDependencies` 已指向 rc.3，但本机
  `pnpm install` 因 store 数据库不可用而失败；`node_modules` 的 rc.3 解析是手工
  对齐的（junction 指向宿主副本）。**在能跑 pnpm 的机器上重装一次即可复现**。

## 生效方式

- **浏览器半体**：重建后刷新页面即可。
- **宿主半体**（`inject` / 事件 / RPC 通道）：需要**重启 DSH**。
